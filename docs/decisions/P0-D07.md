# P0-D07 / TRIMR-8 — approved workflow engine decision

**Status: APPROVED by Andrew on 2026-10-03 (Australia/Sydney), Option A.** Owner: Tony.
The source of truth is now `ADR-011`; `TBC-WORKFLOW-ENGINE` is resolved in place. Approval
includes documentation-only evaluation of unselected Trigger.dev. This decision does not
deploy a scheduler or change a business deadline. Dependency gates still require merge/closure.

## Approved choice and trade-off

**Option A — Supabase `pg_cron` with indexed due-state sweeps and server-side handlers.**
Chosen for launch, based on the local proof below and the existing PostgreSQL architecture.
Each entity keeps its own persisted deadline; a bounded sweep finds due work instead of creating
a recurring cron row for every request. Durable database state, conditional transitions and
reconciliation provide correctness. Cron supplies wake-ups, not exactly-once delivery.

The trade-off is operational work: we must own durable attempts, external-call retries,
reconciliation, backlog-age monitoring and alerts. `pg_cron` is not a complete durable workflow
product. Its lower vendor bill must not be presented as zero engineering cost.

**Option B — Inngest.** Better workflow traces and step orchestration out of the box; adds a
service, SDK and deployed handler integration. The local SDK/server proof works, including
cancellation and duplicate handling. It does not eliminate database guards or reconciliation.

**Option C — Trigger.dev.** Managed task workers and delays are attractive, particularly for
long-running compute. Runtime behavior is **not tested here**: a development project/account
or a separately operated self-hosted platform is needed. It is a candidate, not a demonstrated
equivalent. Self-hosting adds Redis/PostgreSQL, platform and worker operations; its documented
feature set also differs from Cloud. [Self-hosting architecture](https://trigger.dev/docs/self-hosting/overview).

The original criterion required runtime evidence for **each** candidate. Andrew's explicit
Option A approval also amended it: local Supabase/Inngest evidence plus clearly labelled
documentation-only Trigger.dev evaluation is accepted for this spike. The backlog reflects
that amendment. Trigger.dev is **still untested**, not retrospectively marked as passing.
No downstream production integration, security, recovery or capacity test was waived.

## What was actually demonstrated

Run instructions: `scripts/spikes/P0-D07/README.md`. Full results: `docs/qa/P0-D07.md`.

- Real PostgreSQL 17.6 / pg_cron 1.6.4 / PostgREST 16.2 in disposable containers. Final run:
  five-minute expiry applied **610.654 ms late**, never early, one effect. An earlier run was
  834.593 ms late. These are local samples, not a percentile or managed-service SLA.
- Cancellation followed by a stale delivery, ten rounds of eight parallel duplicate calls,
  ten accept/expiry races, dropped schedule reconciliation, paused-sweep recovery, failed cron
  history and API-level denial all passed. A six-hour boundary took **176 ms** to test through
  a private injected clock. No production clock or business config was changed.
- The final bounded sweep processed 1,000 synthetic due rows across ten parallel sessions in
  **189 ms**, alongside 100,000 historical rows. EXPLAIN used the partial due index. This is
  a small database-local contention experiment, not proof of Stripe/Edge throughput.
- Inngest SDK 4.21.1 / CLI 1.45.1 ran locally. Ten short sleeps, cancellation status, completed
  status, a fresh duplicate event and reconciliation passed. Some wake-ups were before their
  millisecond deadline; the handler refused early effects and reconciliation recovered them.
  This demonstrates why a scheduler wake-up is not authority to change state. It does not
  establish the cause or claim that Inngest Cloud has the same timing distribution.

## Approved implementation contract

These directions are recorded upstream in ADR-011, not production code shipped by this spike:

- Persist server-derived deadlines/config snapshots and operation identity with the entity or
  durable work record. Never put a home address, full payload or secret into scheduler arguments.
- Use a fixed set of bounded, indexed due-work scans. Recheck authoritative status/deadline at
  execution; stale jobs no-op. Business calculations remain pure in `packages/domain`; SQL owns
  atomic claims/conditional writes, not a duplicate set of business policies.
- Database-local transition and immutable history commit together. External work must claim and
  commit first, release the lock, perform the provider call with a deterministic server key, then
  reconcile/persist the result. Unknown outcomes remain recoverable, not falsely successful.
  Queue leases, attempt records and notification/outbox handling are still downstream build work.
- Do not depend on cancelling a wake-up for correctness. Reconciliation discovers missing work
  from authoritative entity state, not just from an existing job row. A paused cron misses ticks;
  it must not erase obligations. Alert independently on stale heartbeat and oldest overdue work.
- Preserve the approved Sydney weekly payout calendar and its original scheduled cutoff across
  DST/delayed runs; do not replace it with fixed-UTC cron arithmetic. Preserve the payout ledger,
  bank-outcome reconciliation and no-lock-across-Stripe requirements from P0-D05.
- Test deadline boundaries with injected time only in private test seams. Production gets time
  from the backend and must not expose arbitrary-clock RPCs to mobile roles. Keep a real-time
  scheduling smoke test as well as fast tests; one is not a substitute for the other.

## Switching cost and affected tickets

Before a production implementation exists, changing the recommendation costs another adapter
proof and specification sync. After launch, plan a multi-ticket migration: wrap the seven workflow
families, dual-read/deduplicate during cutover, backfill authoritative pending deadlines, drain or
cancel old deliveries, rebuild alerts, and repeat cancellation/replay/outage/money tests. Preserve
existing operation identities, snapshots and provider references; never reissue a payout merely
because its new scheduler has no record. This is not a library-import-only change. A defensible
day estimate needs the actual runtime design; the vendor spend delta is modelled above.

Generated ADR-011 traceability identified **seven** downstream consumers; the ticket's
`affects` list now includes all seven. Each was synchronized after the KB edit:

| Ticket | Synchronization delivered |
|---|---|
| P2-T03 | Available-until deadline, bounded sweep, protected schedule/handler setup and monitoring/recovery owned within its existing vertical slice. |
| P2-T15 | Request deadline lookup, conditional expiry and recoverable outcome; P3-T06 still owns hold release and provider reconciliation. |
| P3-T11 | Weekly Sydney calendar, frozen cutoff, durable external-operation recovery, no DB locks across calls. |
| P3-T12 | Reliability cooldown/recovery deadlines; preserve immutable offence history. |
| P4-T05 | Throttled ETA due-work scans; stop refreshing inactive bookings; server-only Routes calls. |

Each consumer now names Supabase `pg_cron` and owns its schedule/permissions, protected handler,
operational settings, independent heartbeat/overdue monitoring and recovery tests. Shared
patterns are reused without inventing an unowned central-engine integration ticket. P0-D07
retains its missing Tests-section repair and now records the explicit scope amendment. Its
per-entity wording is corrected to **an individual deadline, not an individual cron job**.
No generated section was edited or regenerated; CI on main owns that update.

P2-T15's old test said acceptance “always wins” a simultaneous expiry race. Corrected it to
the existing conditional-update contract: committed acceptance survives a stale expiry; real
parallel valid transitions produce one legal committed outcome. Added RULE-REQUEST-05 to its
citations. No unconditional acceptance priority, grace period or permission to accept expired
requests was introduced. P4-T11's late-recovery text preserves RULE-COMPLETE-04's actual warning
and full final dispute window; P4-T05 retains the existing throttle rather than replaying missed
ETA refreshes in a burst. P6-T02 makes the approved durable post-commit dispatch requirement
explicit instead of describing it as lossy fire-and-forget.

Historical P0-D02–D05 records retain their at-the-time observations about unresolved later
decisions; they are not the current TBC register. No unrelated product policy was rewritten.
