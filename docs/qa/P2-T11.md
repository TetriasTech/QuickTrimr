# P2-T11 / TRIMR-54 — Barber request inbox UI

**Owner** Andrew. **Ready** Yes. Jira showed TRIMR-23, TRIMR-45 and TRIMR-53
as Done. Andrew approved Option A on 23 November 2026 and resolved
`TBC-AVAIL-ACTIVE-JOB-STATUS` as `RULE-AVAIL-09`.

Open **Booking requests** from a signed-in barber’s home screen. The inbox
shows pending Available Now and Scheduled requests from the running local
API. Each card shows the snapshotted service and price, client display name,
suburb and recorded distance band. A Scheduled card labels its requested
time. The card clock is relative to server time and updates the display only.
Refresh restarts at the first page. The existing availability read is used
for the empty state.

To reproduce the API checks, run `pnpm db:migrate` on the local QuickTrimr
stack, serve the Edge Functions, then run `node scripts/db/verify-barber-inbox.mjs`.
The verifier creates local synthetic users and uses their real Auth JWTs
against PostgREST. It reuses the existing request creation verifier and adds
checks for the job-slot boolean and continuation cursor. See the
[captured API output](evidence/P2-T11/local-api.txt).

Run the six screen tests with
`pnpm --filter @quicktrimr/mobile exec jest --runInBand test/barber-inbox.test.tsx`.
For the native check, use a disposable local barber with an active session,
then give that barber an Available Now and Scheduled request and a separate
Available Now booking at `completed_by_barber`. Leave and reopen the inbox
after the records change. Use a short server-stored deadline on a synthetic
request to check the in-place expiry. Close the pending requests and end the
session to check the unavailable state and navigation to its controls.
