# P2-T09 / TRIMR-52 — Client booking request submission

**Owner** Andrew. **Ready** Yes. All five prerequisite Jira tickets were Done.
The graph check found 108 tickets, 218 defined KB IDs and zero open TBCs.

From discovery, clients can review the barber, service, server price, own saved
address, requested time and cancellation terms before sending. The app preserves
the draft on error. The server checks that the reviewed details still match the
stored snapshots in the creation transaction. Status comes from an owner-scoped
read. The countdown displays the server deadline and asks for fresh status when
it reaches zero.

Run the interaction tests with
`pnpm --filter @quicktrimr/mobile exec jest --runInBand test/booking-request-flow.test.tsx`.
For API evidence, apply the migration with `pnpm db:migrate`, run the local
functions, then use `node scripts/db/verify-booking-review.mjs` on the existing
QuickTrimr local stack with the public SAL dataset. The verifier uses synthetic
users, restores the temporary local config edits and archives its fixtures.

The native run used iPhone 17, iOS 26.5 and the existing development client. The
declined fixture was set in local SQL to exercise the read path. P2-T13 will own
the decline action and P2-T15 will own request expiry processing. The app and
connection used only the local stack and synthetic profiles. The test service
and barber session were archived or disabled and fixture logins soft-deleted.

The new migration adds an index and two authenticated client read RPCs with
explicit owner and stored-role checks. It wraps the existing service-only create
transaction with an optional comparison token so older API consumers keep their
contract. The token cannot set amounts or change request status. None of the read
projections return private barber data or another client's data. The existing
creation audit is part of the rollback when a comparison fails.
