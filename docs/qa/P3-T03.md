# P3-T03 · Stripe webhook router

[TRIMR-62](https://tetrias-tech.atlassian.net/browse/TRIMR-62) · Andrew · 28 November 2026

The existing Stripe webhook verifies the original request bytes, then saves the event ID, type
and resource references before acknowledging a financial event. A protected local worker
reads current Stripe state and compares it with QuickTrimr's saved identities and integer-cent
amounts before applying an outcome. Bank disputes and unmatched refunds create review holds
on linked unpaid earnings. An unresolved event can be replayed after five failed attempts,
with every attempt retained.

## Reproduce locally

Start and migrate the local Supabase stack. Serve the Edge Functions with the existing Quick Trimr
Stripe test key and sandbox account ID, plus a dedicated `STRIPE_WEBHOOK_SECRET` for the local
test. Give the verifier that same environment. The verifier signs requests locally, creates
synthetic Stripe test objects and temporarily installs the versioned scheduler. It removes its
job and Vault credential, cancels unused test holds and soft-deletes the synthetic users.
Unfinished synthetic receipts are parked for review with their attempts intact, so a repeat
run starts with an empty active queue.

```sh
pnpm db:start
pnpm db:migrate
pnpm functions:serve --env-file supabase/.env.local
node --env-file=supabase/.env.local scripts/stripe/verify-financial-webhooks.mjs
node --test supabase/functions/stripe-webhook/test/*.test.mjs
```

For a persistent local schedule, save the local service JWT in Vault as
`stripe_financial_worker_jwt` and apply
[`stripe-webhook-worker.sql`](../../supabase/operations/stripe-webhook-worker.sql) as postgres.
Use the service-only `stripe_financial_worker_health` RPC to inspect heartbeat, oldest queued
due time and the count awaiting replay. After addressing the cause, call
`replay_stripe_financial_event` with the verified event ID. The receipt and attempt history
remain available.

## Audit and follow-up

Audited acknowledgement durability, signature and role boundaries, RLS, provider identity,
integer-cent snapshots, concurrency, immutable audit, replay and scheduler recovery. Seven private
tables deny access through all four attempted Data API verbs. Participant accounts cannot claim
or replay work. The webhook makes read-only provider calls after the queue claim commits.

- **Major, resolved.** The first dispute read revealed a genuine Stripe ID starting with `du_`.
  Validation accepts both observed and previously supported dispute prefixes. The repeat
  sandbox run recorded a real test dispute and preserved booking and payment history.
- **Major, resolved.** A mapped refund still pending at first reconciliation needs a second read
  after acknowledgement. The worker retries pending settlement and the verifier confirms that
  only the settled amount changes the payment total.
- **Minor, resolved.** The local scheduler is bound to the local Supabase gateway. The worker
  uses an indexed due-time scan, a bounded batch and a single recoverable lease.
- **Minor, resolved.** Intentional mismatch and interrupted-work fixtures could stay active
  after a verification run. The verifier now parks its own unfinished fixtures and releases
  their lease after preserving any in-flight attempt.

Option A resolved both webhook decisions as `RULE-PAY-16` and
`CFG-STRIPE-WEBHOOK-WORKER`. `P3-T04` preserves review holds, `P3-T07` binds approved refund
operations, `P3-T10` preserves holds when allocating earnings, and `P3-T11` rechecks already-queued
earnings and verifies actual Stripe transfers and bank payouts. `P5-T09` surfaces provider review
records. The generated backlog indexes are maintained after merge.

This evidence covers the local scheduler and locally signed requests using real sandbox payment,
refund and dispute objects. The pending-refund snapshot and payout provider reads were simulated.
Hosted webhook subscriptions, deployed monitoring and live payouts are follow-on work. This slice
has no UI change. [Workspace checks](evidence/P3-T03/workspace-checks.txt)
