# P3-T06 · Booking request payments

[TRIMR-65](https://tetrias-tech.atlassian.net/browse/TRIMR-65) · Andrew

QuickTrimr saves the owner’s draft and submits it to the barber after verifying the Stripe card
hold. The winning acceptance commits first and starts capture outside that transaction. The
server confirms the booking after it verifies capture. Decline, expiry, client cancellation and
bulk closure persist hold-release work. The server retries it independently of either phone.

After a confirmed capture failure, the owning client can recover the same booking and original
price. The server uses a five-minute Available Now window or a two-hour Scheduled window capped
at the appointment. It verifies the prior payment before reuse or replacement, allows one
replacement, and closes an unpaid booking only after verifying release.

## Reproduce locally

Run the local Supabase stack, apply migrations, and serve the Edge Functions with the
ignored development environment for the Quick Trimr Stripe test account.

```sh
pnpm db:start
pnpm db:migrate
pnpm functions:serve --env-file supabase/.env.local
node --env-file=supabase/.env.local scripts/stripe/verify-payment-capture.mjs
node scripts/db/verify-request-acceptance.mjs --with-decline
node --test packages/domain/test/payment-recovery.test.mjs
```

The original transaction regression uses disposable, authorised fixtures and isolates
the atomic acceptance/decline handler. Pause both local request expiry jobs during its
controlled deadline tests and restore their previous state afterward. The Stripe test drives
the deployed Edge Functions and a temporary lifecycle schedule. It uses a real test hold
and a simulated capture rejection for the known-failure branch.

To install ongoing local payment reconciliation, apply
[request-payment-lifecycle.sql](../../supabase/operations/request-payment-lifecycle.sql)
as postgres with the same local service JWT in Vault as the existing financial worker
(`stripe_financial_worker_jwt`). The existing request expiry schedules still determine when
pending requests expire. The lifecycle schedule processes the resulting captures and releases.

## Audit and handoff

Reviewed original and replacement payment identities, scope checks, RLS, immutable snapshots,
integer cents, state history, provider calls and concurrency. Publication is gated at the inbox,
direct read and acceptance transaction. Capture attempts carry a server-assigned attempt number
into the closing write and idempotency key. A retired identity is preserved on an append-only,
RLS-enabled table outside the exposed schema. Worker claims are short transactions, recheck the
request and booking before persisting a result, and survive lost callers. The log scan records
counts only. [Log scan](evidence/P3-T06/log-scan.txt)

Option A resolved the recovery decision as `RULE-PAY-17` and
`CFG-ACCEPTED-PAYMENT-RECOVERY-WINDOW`. `P4-T01`, `P4-T02` and `P5-T04` read the resulting
unpaid, confirmed or closed booking states. `P3-T03` continues to reconcile signed Stripe events.
`P3-T07` owns refunds of captured funds.

Native evidence is from iPhone 17 with synthetic data. The test logins were archived, unused holds
cleared and the temporary schedule removed. This evidence covers the local test configuration.

The initial run passed the full lifecycle against local Supabase and Stripe test mode. After
Docker became unavailable, PostgreSQL 17.5 with a minimal synthetic schema ran the exact
deadline, trigger, retired-intent table and release SQL from the final migration. It verified
deadline parity, repeated-failure timing, and the retired-intent table's privileges and
append-only protections. Repeated releases wrote exactly one cancellation history row.
[Isolated PostgreSQL check](evidence/P3-T06/postgres-isolated.txt)

The final end-to-end repeat still needs the local Supabase stack. It will also exercise every
Data API verb against the retired-intent table as client and barber participants and as unrelated
users.
