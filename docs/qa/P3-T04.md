# P3-T04 · Barber earnings

[TRIMR-63](https://tetrias-tech.atlassian.net/browse/TRIMR-63) · Andrew · 28 November 2026

Verified capture creates one pending earning in the same transaction as payment confirmation,
booking history and the capture notice. The internal release operation checks the stored booking,
payment, earning and dispute at execution. It records the first availability timestamp and an
audit entry together. The existing Stripe financial review continues to block payout queueing.

## Reproduce

Start the local stack, apply the migrations and serve the Edge Functions. Use the approved
Quick Trimr Stripe test credentials in the ignored local environment file for the sandbox
capture verifier. These verifiers use disposable users, bookings and provider test objects.

```sh
pnpm db:start
pnpm db:migrate
pnpm functions:serve --env-file supabase/.env.local
node scripts/db/verify-barber-earnings.mjs
node --test packages/domain/test/earning-allocation.test.mjs supabase/functions/_shared/services/test/earning-handlers.test.mjs
node --env-file=supabase/.env.local scripts/stripe/verify-payment-capture.mjs
```

The sandbox evidence contains a separate redacted ledger check after the capture verifier.
It counted verified payment receipts joined to pending earnings on their booking IDs.
Cancellation, completion and admin-resolution tests supplied synthetic persisted outcomes
to the real release endpoint. Their owning workflows will use the same release guard when integrated.

## Audit and handoff

The audit covered the capture transaction, RLS and table grants, service RPC and Edge authorization,
money and refund guards, status and audit history, lock order and concurrency. No critical findings
remain. The audit made the existing RLS write denial explicit with table grants for authenticated
and anonymous callers. The direct API returned 403 for authenticated write attempts. The shared request
schema discards server-controlled amounts. The integration test asserts the same result with and
without an injected amount, and rejects an unexpected role field. [Local API](evidence/P3-T04/local-supabase.txt)

`P3-T07` records the approved cancellation on the verified refund mapping, persists the adjusted
earning and calls this release operation. `P4-T09`, `P4-T11` and later admin dispute resolution
lock the booking before changing the eligibility facts. `P3-T10` uses the recorded availability
time and the existing Stripe review hold. Historical capture receipts are backfilled idempotently.
Legacy earnings retain their existing state and are not assigned a fabricated availability time.
There are no changes to commission, refund or payout policy. Generated indexes are left for review
after merge.

The earnings screen belongs to `P3-T05`. Refund initiation, completion actions and payout batching
belong to their owning tickets. [Workspace checks](evidence/P3-T04/workspace-checks.txt) ·
[Log scan](evidence/P3-T04/log-scan.txt)
