# Stripe Connect status and webhook foundation

Ticket P1-T09 / TRIMR-39. Owner Andrew. Verified in the customer sandbox and the local
QuickTrimr Supabase stack on 2026-11-18 Australia/Sydney.

## Implementation

The authenticated `refresh-stripe-connect-status` route resolves the user through Supabase
Auth and checks the stored barber role. It returns the shared four-field status response.
An unlinked barber receives `not_started` and false capability flags. Existing accounts are
read through the pinned Stripe SDK, with the merchant and recipient capabilities combined
with the compatible charge/payout flags and initial submission flag.

The pure mapping is implemented in `packages/domain` under Andrew's approved
`RULE-CONNECT-STATUS-01`. A closed or rejected account is failed. Unknown or unsupported
required capabilities require review. Eligibility requires the verified state plus both
charge and payout gates. Provider errors return a typed failure and preserve the prior
projection.

The `stripe-webhook` route verifies the original raw bytes using Stripe's signing API before
JSON parsing. It accepts legacy account updates and Accounts v2 account, merchant/recipient
capability, requirements and closure notifications. Each triggers a current provider read.
Stored event receipts contain only platform, event ID, type, related account and processing
time. They exclude the raw notification and personal requirement fields.

A short PostgreSQL-owned lease serializes reads for one account. Claiming it commits before
provider I/O. The lease token must still match and be unexpired when the status, safe audit
and event receipt are committed together. A busy webhook or failed commit returns
`processing_failed` so Stripe retries. A duplicate receipt returns a successful duplicate
acknowledgement without a provider call. Failed refreshes release their token. If the
database is unavailable, lease expiry permits a later attempt.

`private.connect_eligible_barbers` is the server-only Stripe eligibility projection for
P2-T04 and later booking/payment consumers. Tests select it before and after a restricted
provider refresh. The remaining discovery filters and search UI belong to their owning
tickets.

## Reproduce

Run the local stack with `pnpm db:migrate`. The ignored `supabase/.env.local` supplies the
existing test API credential, expected sandbox account ID and approved callback URLs.

- `node --test packages/domain/test/connect-verification.test.mjs`
- `node --test supabase/functions/refresh-stripe-connect-status/test/handler.test.mjs supabase/functions/stripe-webhook/test/handler.test.mjs`
- `node scripts/db/verify-connect-status-storage.mjs`
- `node --env-file=supabase/.env.local scripts/db/verify-stripe-connect-status.mjs /absolute/path/to/stripe`

Use the official Stripe CLI. Version 1.55.12 was downloaded from Stripe's GitHub release and
checked against its published macOS checksum for this run. The live verifier starts a local
listener for the listed v2 thin events, captures its signing secret privately, and starts the
actual Edge runtime with a temporary 0600 environment file. It forwards the original signed
bytes through a loopback bridge, then replays the same bytes and signature concurrently.
It drains CLI/runtime output privately, stops its child processes and deletes the temporary
environment file afterward. The test environment file is distinct from the operator's file.
The command temporarily takes ownership of local Edge serving for the QuickTrimr stack.

The verifier creates two disposable local barbers and two synthetic Stripe accounts through
P1-T07. It reads the account ID from private storage. Each restricted provider account is
paired with a deliberately verified local fixture to exercise loss of eligibility. This
setup uses service-only fixture calls. A metadata-only Stripe update generates the real
signed event. The event is independently retrieved through Stripe's Events API. The
account remains restricted in Stripe throughout this test. It performs no payment or
account-holder onboarding submission.

## Evidence and acceptance

The final [sandbox result](evidence/P1-T09-live.json) records two actual signed events,
12 simultaneous first deliveries, 72 duplicate replays and zero duplicate effects. Maximum
acknowledgement time was 1,072 ms. Both restricted fixtures were excluded. The focused domain
and handler suite passed 13 tests. Repository lint, typecheck, tests, formatting, client-env,
API contract, seed and graph checks passed.

| Criterion | Reproducible evidence |
| --- | --- |
| Map and persist provider status | All five approved states and each required capability are covered in domain tests. The real endpoint returns unlinked and pending states and persists the restricted account as requires_review. |
| Reject invalid signatures without writes | Unit tests reject missing, stale and tampered signatures before processing. The real event's tampered raw bytes return 400 and leave receipt count unchanged. |
| Duplicate delivery produces one effect | Two actual signed events each arrive in six simultaneous requests. Three additional batches of 12 replays per event return duplicate acknowledgements. Stored state, receipt count and audit count remain stable. |
| Persist event IDs | The actual events have one receipt each. A local competing-receipt test forces the final insert to fail and proves the state and audit writes roll back. |
| Restriction excludes the barber | The private eligibility query returns the primed fixture, then excludes it after refreshing the genuinely restricted provider account. Both test barbers are checked. |
| Audit status transitions | Unchanged refreshes append no extra audit. Restriction audits contain previous/new safe flags, null system attribution and an action-required signal. |
| Exclude secrets and payloads | Responses are asserted field by field. Evidence contains aggregate results. The webhook passes only a safe projection to storage. Key and raw-event values remain private. |
| Acknowledge promptly | The live output captures maximum acknowledgement time. Duplicate and unknown-account paths avoid provider I/O. Provider requests have bounded timeouts with no SDK retries in ingress processing. |

The storage verifier additionally demonstrates expired-holder fencing, busy leases,
append-only receipt protection and loss of eligibility on a committed restriction. Its
provider IDs are fictional. Fault-injected provider failures are covered by focused handler
tests.
