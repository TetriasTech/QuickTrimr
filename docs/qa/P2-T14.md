# P2-T14 / TRIMR-57 — Barber accept and decline UI

**Owner** Andrew. **Ready** Yes. P2-T11, P2-T12 and P2-T13 were Done in Jira
before implementation. [TRIMR-57](https://tetrias-tech.atlassian.net/browse/TRIMR-57).

Barbers can respond to Available Now and Scheduled requests from the inbox.
Accept requires confirmation. After a successful accept, View booking status
opens the returned booking, using the owner's authenticated read of
`id,status` to show its current state. Decline uses the existing endpoint
without an optional reason.

## Verification

On iPhone 17 (iOS 26.5), sign into a local synthetic barber account with
one pending Available Now request and one pending Scheduled request. Open
Booking requests. Cancel the Available Now confirmation, reopen it and
confirm. Open View booking status and then return to the inbox and decline
the Scheduled request. This run persisted one pending-payment booking and
one declined request. [Database result](evidence/P2-T14/native-api.txt).

Run the focused mobile tests with
`pnpm --filter @quicktrimr/mobile exec jest --runInBand test/barber-inbox.test.tsx`.
[Mobile test output](evidence/P2-T14/mobile-tests.txt).

Run `node scripts/db/verify-request-acceptance.mjs --with-decline` against
the running local Supabase stack and Edge Functions. The verifier sends
requests using real local JWTs and observes contention in Postgres.
[API regression output](evidence/P2-T14/api-regression.txt).

## Audit

Audited the P2-T14 mobile routes, API adapter, cache, UI, validation and
tests against QuickTrimr's audit checklist. The existing Edge Functions
verify role and ownership, enforce expiry and availability, and write
history and audit records. The foreign-barber REST read of the identical
`id,status` projection returned an empty collection. The status request
has an exact booking ID and selects two columns. It uses the existing
booking RLS policy and a user-scoped query key. The app performs one first-page
refresh per completed action and reads standing after the unavailable
conflict. The countdown only affects presentation and available controls.
Shared schemas, state components, badges and the native confirmation are
reused. No migration or provider integration was required.

**Verdict** Zero Critical, zero Major, two Minor fixed. The standing panel
handles availability loading and retry while it is shown, avoiding duplicate
messages in the empty inbox. The action feedback now distinguishes session,
permission and validation failures from a response whose result is unknown.
