**UNDERSTOOD** Barbers choose their own categories and prices within the current
catalogue bounds. Editing or disabling a service must preserve historical bookings.
This slice delivers storage constraints, protected mutations, a real mobile screen
and evidence of ownership denial, exact cents and recovery from failures.

**DONE** The setup and barber journeys link to Services & prices. It loads bounded
joined pages of active categories and only the caller's services, with no default
category or price. Each row uses a native Expo switch and the shared input/card/button
components. One React Hook Form retains row drafts across virtualization; failed saves
and refreshes preserve edits. The screen includes loading, error, retry and empty states.
It explains that existing bookings do not change and that pricing alone does not make
a barber eligible for paid bookings.

`upsert-barber-service` and `archive-barber-service` verify Auth and the stored barber
role before parsing the mutation or querying service data. A service-only database
function rechecks the role and ownership. Its transaction locks the owner profile,
then the category, then the service; P1-T10's price-integrity trigger remains in place.
No network/provider call occurs inside a database transaction.

A unique barber/category pair retains the same service ID across changes and
reactivation. `enabled` is derived from `archived_at`; `enabled:false` archives.
The dedicated archive operation works even after its category is archived, is
idempotent and returns the same 404 for unknown and foreign service IDs. Direct table
DML is revoked, including service-key writes. DELETE/TRUNCATE and ownership/category
reassignment are guarded. Existing owner/admin read policies remain intact.

Every real mutation appends exact safe previous/new values and actor attribution.
Duplicate identical requests and no-ops do not append extra mutation audits.

## Reproduce

Use the local QuickTrimr stack with Edge serving. Never print local keys or Auth responses.

```sh
node scripts/db/local.mjs migrate
node --test packages/domain/test/service-price.test.mjs
node --test supabase/functions/_shared/catalogue/test/handler.test.mjs supabase/functions/_shared/services/test/barber-service-handler.test.mjs
pnpm --filter @quicktrimr/mobile exec jest --runInBand barber-services
node scripts/db/verify-barber-services.mjs
node scripts/db/verify-barber-service-migration.mjs
node scripts/db/verify-service-category-migration.mjs
```

The live verifier creates disposable local Auth users, categories, services and booking
fixtures. Booking creation itself belongs to P2-T08; SQL establishes the pre-existing
snapshot fixture for this test. Actual category/service changes use authenticated Edge
requests. Fixture categories are archived through the API afterward; referenced identities
and history remain. Evidence contains aggregate checks/statuses, not credentials or profiles.

Concurrency is genuine: six simultaneous identical upserts return one row/ID/audit; four
simultaneous archives have one effect. Six price/category races observe a blocked API request
via `pg_blocking_pids`, then execute the competing request. Three runs exercise each winner.
Each committed active price is checked against the category's current range. The barriers
are test-only transactions, released in `finally`; application transactions perform only SQL.

The migration verifier uses a disposable database in the QuickTrimr container, copying
Auth/Storage DDL only and replaying all 12 repository migrations. It proves duplicate legacy
pairs cause an atomic failure before retrying a corrected synthetic fixture; it never chooses
between historical rows in the actual migration. Seed reruns preserve the upgraded data.
The shared isolation helper is also regression-tested against P1-T10's original 11-migration
boundary. Neither the user's development stack nor installed address datasets are reset.

The native walkthrough used the real local backend. A temporary audit failure for the test
service demonstrated failed-save rollback; a temporary revocation of the public catalogue
description read grant demonstrated loading/error/retry. Both probes were removed/restored.
The on-screen decimal keyboard leaves Save visible and reachable; its temporary visibility
was restored. One existing root session/profile retry was also needed before reopening
pricing; it recovered and the subsequent persisted read and pricing retry succeeded.

## Migration and boundaries

`20261119130000_barber_services_and_pricing.sql` changes the existing `barber_services`
constraints, guards and grants and adds the private JSON helper/service-only mutation
function. No new application table or paid-booking eligibility grant is introduced.
The migration deliberately fails for duplicate legacy barber/category pairs; review those
rows and their history explicitly before retrying rather than silently merging/deleting them.

The destructive historical foundation runners are not acceptance gates for this slice:
their earlier exact-schema/profile assumptions predate Phase 1. Catalogue-specific fixture
expectations were maintained for the new uniqueness and audited-write path. In addition,
P1-T10's old API verifier used raw service-key price writes as fixtures; that historical
writer is now deliberately denied. The current P1-T11 verifier supersedes that fixture path
and tests category/price races through both real mutation APIs. Required repository tests,
dedicated live APIs, isolated migrations and native flow all pass.

Native interaction was exercised on iOS. Android interaction, production deployment,
public profile/search and actual booking/payment creation were not part of this run.
