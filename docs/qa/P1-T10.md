# Service category management

P1-T10 / [TRIMR-40](https://tetrias-tech.atlassian.net/browse/TRIMR-40). Owner Andrew.
Verified on 2026-11-19 against the running local QuickTrimr Auth, Edge and PostgREST services.

## Delivered behaviour

Admins create, update and archive categories through three authenticated Edge routes.
The shared handler verifies the bearer with Auth, reads only that caller's stored role,
then validates the request and invokes a service-only database function. The transaction
rechecks the admin role, locks the category and appends the exact safe previous/new audit.
Client bodies and signed user/app metadata cannot grant admin access. Direct category
table writes are revoked, including service-key writes; mutations use the audited function.

The active catalogue is a PostgREST query with `archived_at=is.null`, ordered by
`display_order,slug,id`, selecting only catalogue fields. All authenticated identities can
read it, including an identity awaiting profile creation. The shared
`serviceCategoryListSchema` validates the camelCase projection. Archived metadata remains
visible to admins and the owners of linked services/bookings. An unrelated user cannot
enumerate archived categories. Category DELETE and TRUNCATE are guarded; slugs are immutable.

Andrew approved `RULE-SERVICE-06`: a new range must contain every active service price.
Exact boundary prices pass, archived services do not block the change, and booking
snapshots remain untouched. A category transaction locks the parent `FOR UPDATE`; linked
service writes take `FOR SHARE` before checking the current bounds and archive marker.
The active-price index supports two `EXISTS` probes without loading every service price.
There is no external call while these locks are held.

## Reproduce

Use the existing local QuickTrimr stack (`http://127.0.0.1:55321`) with migrations applied
and the local Edge runtime running. No hosted credentials or Stripe calls are needed.

```sh
node scripts/db/local.mjs migrate
node --test supabase/functions/_shared/catalogue/test/handler.test.mjs
node scripts/db/verify-service-categories.mjs
node scripts/db/verify-service-category-migration.mjs
```

The API verifier creates synthetic Auth identities and category/service/booking fixtures.
It retains referenced history and archives its disposable categories through the actual
API. Temporary fault/race triggers are removed in `finally` blocks. Evidence contains only
check labels and aggregate HTTP outcomes, with no credentials, personal fields or payloads.

The migration verifier uses a separate randomly named database in the QuickTrimr container,
copies platform Auth/Storage DDL only and replays repository migrations. It removes that
database afterward. The existing stack and installed address datasets are not reset.
Platform DDL is restored with the container's existing local admin credential held internally;
repository migrations execute as `postgres`. This is schema/upgrade evidence, not an Auth or
Storage platform certification.

## Migration and rollout

`20261119120000_service_category_management.sql` changes `service_categories` and adds
`barber_services.archived_at`; no new application table is introduced. Existing RLS remains
enabled. Five approved launch identities are backfilled or inserted and initialized in the
append-only audit. Seeds use the full catalogue shape and remain insert-only.

The migration deliberately fails and rolls back for an unmapped legacy category identity
or a legacy active service price outside the approved range. Resolve those data mappings or
prices explicitly before retrying; the migration never guesses metadata or deletes history.
The isolated verifier exercises both failures, a clean replay, an identity-only seeded
upgrade and two non-destructive seed reruns.
