# TRIMR-37 Stripe Connect onboarding verification

Backlog `P1-T07`. Owner Andrew. The endpoint creates or resumes a sandbox-only Express
account for the authenticated barber. It issues a Stripe-hosted onboarding link after the
account association is committed and the manual payout schedule is verified. The account
status in this response describes the onboarding link flow. Booking eligibility remains the
server's `RULE-ONBOARD-04` charge and payout checks.

## Reproduce

1. Use the local QuickTrimr stack. Apply `pnpm db:migrate`.
2. Configure the existing ignored `supabase/.env.local` with the customer sandbox API
   credential, sandbox account ID and the approved `CFG-DEV-PROVIDER-URLS` callbacks. The
   account create uses a stable synthetic contact email required by Stripe's recipient
   configuration. The hosted form collects the account holder's details.
3. Run `pnpm functions:serve --env-file supabase/.env.local`.
4. Run `node --env-file=supabase/.env.local scripts/db/verify-stripe-connect-onboarding.mjs`.
   This creates disposable local Auth users and two synthetic connected accounts in the
   configured Stripe sandbox. Each round sends four parallel requests and one repeat. It
   reads the account and payout settings from Stripe, verifies one account per intent in the
   sandbox account list, and checks link shape, safe audit attribution and API-level denial.
5. Run `node --test supabase/functions/create-stripe-connect-onboarding-link/test/handler.test.mjs`
   for typed failure responses, a dropped persistence write and the replay-window boundary.

## Results on 2026-11-17

- Local migration applied. PostgreSQL catalogue checks confirmed RLS is enabled and client
  database roles lack read and write grants on the new table. Authenticated API attempts for
  GET, POST, PATCH and DELETE through the private schema and direct calls to all three service
  RPCs were denied.
- The device-independent live verifier passed. Two disposable barbers each sent four parallel
  first requests and a repeat. Each round returned five distinct, unexpired Stripe links,
  saved one account, appended one account creation audit and five link audits, and found one
  account with that operation ID in Stripe's sandbox list. The repeat restored a deliberately
  changed daily schedule to manual. The sandbox served or redirected the hosted URL.
- Eight focused handler tests passed, including provider outage, dropped account persistence,
  link issue failure and typed errors. The failures were injected locally. The sandbox run
  exercised no payments, payouts, connected-account terms or bank-detail submissions.

## Provider facts and recovery

Stripe Accounts v2 scopes idempotency to the operation and sandbox for 30 days. The Edge
Function commits the operation ahead of the call, maps its opaque ID to Stripe metadata and
saves the successful account ID and creation audit in one database transaction. Provider
declarations and payout settings are read on reused accounts. A daily or weekly provider
schedule is reset to manual and confirmed with a fresh Balance Settings read before link
issue. The platform-wide controls are documented in the
[Phase 0 sandbox follow-up](P0-T18.md#2026-11-17-sandbox-payout-follow-up).
[Stripe v2 idempotency](https://docs.stripe.com/api-v2-overview#idempotency)
[Stripe payout schedule API](https://docs.stripe.com/connect/manage-payout-schedule)

After an ambiguous failure the same intent and sandbox recover the original provider
operation within the replay window. The handler returns `409 stripe_account_reconciliation_required`
once that period is nearly exhausted. For reconciliation, match the saved `operation_id` with
`quicktrimr_connect_operation` in the configured sandbox's account list and Workbench request
history. Verify the match, sandbox and reviewed payout configuration before recording the
original ID against the original reservation with the service-only
`record_stripe_connect_account` database function. Leave conflicting or inconclusive matches
for operator investigation. Keep account links and provider responses in the Stripe sandbox.
Stripe-hosted UI and return/refresh navigation in the app belong to `P1-T08`. Webhooks and
persisted eligibility refresh belong to `P1-T09`.
