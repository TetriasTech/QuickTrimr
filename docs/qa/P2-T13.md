# P2-T13 / TRIMR-56 — Decline booking request

**Owner** Andrew. **Ready** Yes. The request creator, inbox, Available Now
outcome hook and acceptance endpoint are Done in Jira. Andrew's Option A
approval on 26 November 2026 is recorded in `RULE-REQUEST-07` and resolves
`TBC-REQUEST-DECLINE-REASON`.

`POST /functions/v1/decline-booking-request` uses the verified barber's ID
and accepts `requestId` plus an optional reason code. The database locks the
barber profile and the addressed request in `P2-T12` order, then checks the
deadline using the server clock. The conditional status change, any response
receipt and the audit share one transaction. Decline has no booking row or
booking status history to append.

The optional code is `too_far`, `unavailable`, `service_unavailable` or
`other`. A supplied code appears only in `booking_request.declined` audit
metadata. Omission creates the normal audit without a code. The client status
projection and the shared response contain no code.
