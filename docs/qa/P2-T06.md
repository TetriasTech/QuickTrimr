## Delivered

Client discovery uses one virtualised FlatList for the filter header and result
cards. “Show barbers” collapses the controls to a search summary; “Change filters”
reopens them. Cards reuse the public identity schema, Avatar, Card and integer-cent
formatter, plus the profile's rating/initials presentation. They show the selected
category price, SAL label, approved distance band, honest rating and availability.
The accessible button label includes those public fields. No exact distance,
barber coordinate, home address or private contact field is rendered.

Search uses TanStack infinite queries with the existing opaque cursor, preserving
server order. Repeated end events share the in-flight continuation. Refresh cancels
in-flight work and drops the old cursor chain before fetching the first page.
Filter changes retain only local selections, clear the selected barber and use a
new user/filter key. Pages are live; stable traversal assumes unchanged data.
Errors preserve loaded cards with recovery guidance, and never claim no matches. Refresh/loading feedback is above the results; continuation errors remain beside the page controls. Explicit refresh scrolls to the top before starting the new traversal.
Empty results offer editable radius/service controls and Scheduled without
inventing a date. Initial loading and offline failure are separate states.

A card saves the barber ID and routes only barber/category IDs to the existing
profile. Its optional selected-category lookup returns one current active public
service independently of the profile's bounded service page, so category 25 is
visible without fetching all preceding pages. Archived selections show unavailable.
A changed live price is read from the server; no route amount or booking snapshot
is created here. The latest profile page supplies the selected price.

## Data and security

Migration `20261121020000_discovery_selected_service.sql` adds a four-argument
service-only profile RPC and delegates the preserved three-argument API to it.
No tables, policies or grants to mobile roles are added. The selected lookup is
bounded by the existing `(barber_id, service_category_id)` unique constraint.
Both signatures retain service-only execution and recheck stored client role.
Shared strict schemas and the Edge/mobile adapters verify selected category identity.

Isolated replay and populated upgrade preserve services, bookings and audits.
Real Auth → Edge → database tests cover missing/invalid JWT, wrong stored role,
field validation, private projection allowlists, and GET/POST/PATCH/DELETE denial
on raw profile storage. Search/profile recheck Connect eligibility. Fixtures are
explicit synthetic local eligibility facts, not Stripe verification. Cleanup
archives service-backed records and retains immutable history; no DB reset,
customer data, Stripe call or Google call is involved.

Money movement, booking status/history, timers and scheduled enforcement are N/A:
this is a read-only discovery/profile slice. Existing booking snapshots are untouched.
