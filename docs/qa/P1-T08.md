# Barber Stripe Connect onboarding UI

Andrew owns [TRIMR-38](https://tetrias-tech.atlassian.net/browse/TRIMR-38) / P1-T08.
P1-T06, P1-T07 and P1-T09 were Done before implementation. This slice adds the mobile
card and browser orchestration over the merged link and status endpoints. It changes
no database tables, Edge Functions, provider account settings or payment operations.

## Behavior

The same card appears in the incomplete barber profile journey, the completed barber
journey and the Connect callback route. All five shared verification states have
distinct copy and next actions. Every unverified state has a non-dismissible paid
booking warning. A verified account has a completed state and no start action.

Every start or resume obtains a new account link. The link stays in memory for the
browser call, outside query data, persisted storage and route parameters. The shared
API boundary validates both endpoints and sends an empty request with the current
bearer token. A changed or missing session stops the request. The server derives the
barber identity and role.

The browser uses the SDK-matched `expo-web-browser` auth session. It checks the server
after return, cancel, dismiss or browser failure. A refresh callback requests a fresh
link and reopens the browser; one automatic renewal prevents a redirect loop. An
already-expired response is not opened. Only the server status can show verification.
The global session-scoped controller survives callback navigation and suppresses a
second browser launch when Android also routes the return link. A cold refresh callback
can resume from a newly mounted provider. Returning to the foreground outside an active
browser session also checks status, without polling. [Expo SDK 57 browser reference](https://docs.expo.dev/versions/v57.0.0/sdk/webbrowser/).

A status outage preserves the prior query data and labels it as last checked, removes
the current completed claim, and offers retry. No error or redirect changes the stored
verification state or booking eligibility. The latter remains the backend's decision
under RULE-ONBOARD-04 and RULE-CONNECT-STATUS-01.
Status queries use the existing shared bounded retry policy for transient failures.
Retry and foreground refresh calls share an in-flight query instead of cancelling it
and starting another provider read.


For the real API check, run the local QuickTrimr Supabase stack with its existing

```sh
pnpm db:start

# In another shell:
node apps/mobile/test/verify-connect-live.mjs
```

The verifier creates disposable local barber and client users. It checks both real
endpoints through the production mobile adapter, then exercises the flow with real

and a forged completion return, two distinct fresh links, client denial and signed-out
denial. It performs no onboarding submission or payment. Local users are soft deleted
to preserve immutable audit attribution; synthetic sandbox accounts remain. The
[captured result](evidence/P1-T08-live.json) explicitly records that no native browser
was exercised by this command.

## Local native callback setup

The existing approved development callback URLs use loopback port 4242. The new bridge
reads their paths and port from CFG-DEV-PROVIDER-URLS and the app scheme from app.json.
It redirects only the two configured paths to the app's Connect route with an action
notification. Incoming query fields are discarded. It binds to loopback, accepts no
credentials and logs no links. Do not run the diagnostic probe on the same port.

For an installed development build:

```sh
node scripts/stripe/mobile-callbacks.mjs
```

For Expo Go using a Metro server started with `--localhost --port 8081`:

```sh
node scripts/stripe/mobile-callbacks.mjs exp://127.0.0.1:8081/--/connect
```

On a Mac where localhost resolves to IPv6 first, launch Metro with Node's
`--dns-result-order=ipv4first` option to match that IPv4 callback target. For example,
from `apps/mobile`, use `node --dns-result-order=ipv4first node_modules/expo/bin/cli start
--go --localhost --port 8081 --clear`. Reopen the project from Expo Go's home screen
after replacing a stale Metro process so its native context loads the fresh manifest.

Use the public local Supabase URL and anon key in the app's ignored `.env.local`.
For an Android emulator, reverse the loopback ports for Metro, the local API and the
callback bridge before testing. The checked-in development placeholders are for local
testing; hosted/mobile distribution needs its environment's approved HTTPS callbacks.
This ticket does not switch the customer account to live mode.

## Quality and audit

The focused suite passed 10 flow/API tests, 11 native component tests and 2 bridge tests.
The complete mobile suite passed 29 Node tests and 11 native component tests. Repository
tests, lint, typecheck, formatting, client environment boundary and ticket graph checks
passed. Android and iOS exports passed.

Audited the P1-T08 UI, route guards, session-scoped API boundary, callback flow, local
bridge and tests against QUICKTRIMR_AUDIT_PROMPT.md A–F. One Major runtime compatibility
finding and one Minor duplicate-read finding fixed; no unresolved findings. Checks included JWT-derived identity, redirect mistrust, cancellation,
stale status errors, safe query contents, callback routing, shared schemas/primitives,
no polling, and scope boundaries. The review caught the cold-callback provider effect
ordering; initialization now precedes the route effect and a native component test
reproduces that case. The actual iPhone run exposed another issue: React Native's installed
`abort-controller` polyfill has no `throwIfAborted` method. The flow now checks the portable
`aborted` flag and raises a named cancellation error. A regression test supplies that
native signal surface and verifies both successful flow and cancellation. Native Start
and resume then opened Stripe successfully. The status query also reuses the shared
bounded transient-error retry instead of disabling it.
The outage walkthrough exposed that repeated retry taps could cancel and restart a
provider read. Query refresh now sets `cancelRefetch: false`. The regression test holds
the first request unresolved while a second tap arrives and asserts one invocation;
it failed with two invocations before the fix and passes with one afterward.

No KB or backlog changes. RULE-ONBOARD-04, RULE-CONNECT-STATUS-01, RULE-COPY-01 and
ENUM-VERIFICATION-STATUS remain unchanged. P1-T11 still owns service pricing and final
publication readiness. P3-T05 must use the same server-derived Connect state for earnings.
Generated backlog sections 8/9 were left untouched.

## Native verification

On 2026-11-19 Australia/Sydney, the iPhone 17 / iOS 26.5 run used disposable local barbers
and the customer sandbox. Start from an unlinked fixture created exactly one association
and issued a hosted link. The hosted page displayed Stripe's test-data banner. No
onboarding form, identity/bank data or terms were submitted. Closing the browser left
pending with the warning. Resume reopened Stripe. Its own Return link reached the local
bridge, closed the browser and triggered a server status check. Some provider reads
timed out; safe retry recovered pending, without a redirect-based verification claim.
See the [aggregate native evidence](evidence/P1-T08-native.json) and screenshots above.

After the Safari handoff, a stale Metro/native context needed a cleared cache and a
fresh project launch. The cold refresh callback then automatically requested a new
hosted session. A service-only aggregate confirmed one connected-account association
throughout and an increase from one issued link to two. The renewed Stripe page opened
on the simulator; closing it rechecked the server and retained pending.

The refresh URL was injected through the approved local bridge to simulate the expiry
redirect. Already-expired timestamp responses and repeated refresh redirects are covered
by the focused flow tests. Verified, failed and requires_review presentation uses native
component fixtures; the synthetic provider accounts were not submitted for verification.

For error evidence, only the local QuickTrimr Edge-runtime container was stopped. The
app retained last-checked pending, displayed loading and retry, and recovered pending
after the same container was restarted. The protected endpoint then returned the expected
401 to an unauthenticated request, confirming service restoration. No database, provider
account configuration or other project was changed. Screenshots contain no bearer links,
tokens, entered contact details or credentials. No required acceptance verification remains.
