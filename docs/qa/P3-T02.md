# P3-T02 · Payment capture

[TRIMR-61](https://tetrias-tech.atlassian.net/browse/TRIMR-61) · Andrew · 28 November 2026

After an accepted request has an eligible Stripe hold, the server claims the capture in a short
transaction. It sends the full saved amount to Stripe, using the payment ID as the idempotency
key. A second transaction confirms the booking only when Stripe proves the full capture. It
writes history, audit and a durable in-app outcome together. The client and accepting barber
see the result on their existing status screens.

## Acceptance evidence

| Criterion | Evidence |
| --- | --- |
| Valid capture confirms the booking and records history | Two synthetic Scheduled bookings were accepted through the existing barber endpoint, then captured through the server endpoint. Each had exactly one `paid_confirmed` transition. [Sandbox runs](evidence/P3-T02/stripe-sandbox.txt) |
| A duplicate capture charges once | The repeated request returned the same capture with `idempotent: true`. Stripe listed one captured charge per PaymentIntent. The Dashboard confirmed a successful A$45.03 capture for the additional native QA booking. [Dashboard](evidence/P3-T02/stripe-dashboard.txt) |
| Parallel capture charges once in repeated runs | Two runs of eight parallel calls, each with varied supplied keys and amounts. Both produced one captured charge, one history transition, one outcome audit and one notice event. [Sandbox runs](evidence/P3-T02/stripe-sandbox.txt) |
| Server derives the key | The Stripe adapter uses `quicktrimr:capture:<paymentId>` from the claimed payment row. Eight different supplied keys converged on the same result in each live run. [Sandbox runs](evidence/P3-T02/stripe-sandbox.txt) |
| Failed capture leaves the booking awaiting payment | With a real authorised test hold, the verifier injected a rejection at the provider boundary. It asserted HTTP 402, `capture_failed`, `accepted_pending_payment` and zero paid confirmations. [Sandbox runs](evidence/P3-T02/stripe-sandbox.txt) |
| Expired authorisation returns a distinct error | The stored deadline reached the test database clock. The endpoint returned `409 authorisation_expired` and Stripe showed zero captured cents. The unit test also covers the exact provider deadline. [Handler tests](evidence/P3-T02/handler-tests.txt) |
| No database lock crosses Stripe I/O | The verifier paused at the provider boundary. An independent transaction locked the request, booking and payment rows within a 750 ms lock timeout. All 32 concurrent status reads completed before the pause was released. [Sandbox runs](evidence/P3-T02/stripe-sandbox.txt) |
| Both participants see success and confirmed failure | Both roles passed raw API field checks and the two existing iPhone screens showed both outcomes. Foreign client/barber access returned null, and the private event table was unreachable through public API verbs. [iPhone evidence](#iphone-evidence) |
| Capture uses the authorised integer amount | Stripe and the saved payment agreed on 4,503 gross cents. The commission and barber net stayed at 900 and 3,603 cents. All three captured QA payments stored the actual Stripe processing fee. [Sandbox runs](evidence/P3-T02/stripe-sandbox.txt) |
| Success and failure both append audit entries | Each definitive outcome added exactly one audit entry. The rejected capture added no paid confirmation history. [Sandbox runs](evidence/P3-T02/stripe-sandbox.txt) |

## Reproduce

Start and migrate the local Supabase stack and serve the Edge Functions with the existing Quick
Trimr Stripe sandbox configuration. The verifier creates synthetic users and card holds,
captures synthetic test payments and releases unused holds.

```sh
pnpm db:start
pnpm db:migrate
pnpm functions:serve --env-file supabase/.env.local
node --env-file=supabase/.env.local scripts/stripe/verify-payment-capture.mjs
node --test supabase/functions/capture-authorised-payment/test/handler.test.mjs
```

## Audit and follow-on work

Audited the migration, private event grants and projections, payment state machine, provider
adapter, Edge handler, status screens and tests. Fixed an ambiguous SQL variable discovered
by the live verifier. Used Stripe's default final capture because the explicit parameter
requires multicapture support in the sandbox. Both fixes were verified by repeat sandbox
and native checks. No critical or major findings remain for this slice.
